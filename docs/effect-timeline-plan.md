## 1. P0 分组时间轴（结构性，先做）

**语义**：同组的多条消息**并排**显示，共享一套全屏 border 与呼吸；组内逐条入场，整组一起退场。

- 归组键：新增 `-group <名>`；没写时退到 `tag` → 再退到 `-from` → 再退到档位（`color+urgent`）。
- 组的 border 档位 = 组内**最高档**（error > warn > info），时长取组内最长单条。
- 时间轴：第 1 条入场 0.5 s → 第 2 条入场 0.5 s → …；每条驻留 `ScreenSeconds`（默认 3 s）。
  **组的到期时刻 = 最后一条的（入场完成 + 驻留）**，不是从第一条起算。
- 组显示期间**新加入**一条同类消息 → 插到组尾，并把**整组**的到期时刻按"从它加入时起算"重算（用户明确要求）。
- 队列改造点：`EffectJob` 增加 `Group` 与 `Entered`；`EffectSchedule.Tick/Pump` 从"选一条播"改为"选一组播 + 组内追加"；`Preempt`（紧急抢屏）保持整组级别。

**易用性调整（我的判断，需要你确认的在 §5）**

1. 一屏最多 **4 行**，第 5 条起继续排队（12 条堆满屏等于没有警告）。
2. 组总时长封顶 **12 s**（8 条 × 3 s = 24 s 会长期挡屏幕），封顶后按 FIFO 逐条退出而不是整组硬撑。
3. 「重新计时」只对**同组**生效，避免一个高频子代理把屏幕永久锁住。

## 2. P1 入场 / 驻留 / 退场动画（四步，按你给的顺序）

1. **粒子块扫入**：一条高亮斜线团从屏右向左快速平移（0.5 s，`TranslateTransform.X`）。
2. **警戒线跟着拉出**：斜线层套一个 `RectangleGeometry` clip，clip 的 `RectAnimation` 跟随粒子块右缘推进——扫到哪，线拉到哪。
3. **驻留**：斜线层 `Viewport.X` 缓慢循环平移（持续感），**文本保持居中不动**（文本不挂在平移层上）。
4. **退场**：clip 反向收 + 整层向右扫出；组的 border 同时结束。

可行性：全部是 WPF 标准动画能力；`Viewport` 是 DP 可用 `RectAnimationUsingKeyFrames`，平移层用 `TranslateTransform` 已有先例。**风险点**：`Tape` 现在是三列 Grid + 单一 `TapeText`，改成"多行 + 每行独立 clip/平移层"要把每行做成一个 `BannerRow` 控件（新建 `Views/BannerRow.xaml.cs` 或代码构建），这是 P0/P1 的共同前置。

## 5. 三处待拍板 → 落地时的决定（2026-09-22）

1. **一屏最多 4 行**（`EffectSchedule.MaxRows`，效果窗共用同一个数）；**不给整组封顶时长**——
   原稿提的 12 s 会咬掉合法的长告警（UPS 一条本来就驻留 20 s）。收屏另有 `xa off` / `xa -k`。
2. **归组优先级 `-group` > `-tag` > `-from`**，三者都不写 = **不成组**（照旧排队）。
   原稿的「退到档位」被否掉：那样所有裸消息会彼此成组，等于把「一条播完才播下一条」这条拿真事故换来的规矩废了。
3. **默认档 8 s / 首尾各 0.5 s / 58 号 / 带宽 60**（`EffectCommand` 的默认值与彩蛋共用一份）。
   淡入那一段同时是扫描头擦边的时长（夹在 0.15–1.5 s），所以 `-s warn 6 1 1` 看得见一道 1 秒的擦边。

另两处与原稿不同：
- **彩蛋没有改走队列**：`KeywordWatcher` 与夹具都直接调 `EffectsWindow.ShowBanner`（签名是刻意保住的），
  改成入队会牵动关键词侧的测试口径；本次只统一**模板**（同一个 `BannerRow`、同一份字号与节奏），
  排队语义留给命令行。若之后要彩蛋也排队，改点是 `KeywordWatcher.Apply/Trigger` 四处调用。
- ~~**没做「模块模板基类」**：立绘需要的只是「面板上能改的参数 + 落盘」，监视模块协议已经给了；
  再造一层基类就是为假设中的第二个使用者写空壳。设置面是 `icon-backdrop` 这张卡。~~
  → **这条决定在第四轮被用户否掉并反做**，见 §9：立绘参数属于「这个 IDE 的消息长什么样」，
  抽象基类才是它的落点，独立设置卡只是把六行参数挂在了一个不认识任何 IDE 的地方。

用户看真机后提了两条，都成立：

1. **「红色是直接叠上去的」**——边框换级时只是把四支画刷换成新配的纯色，没有过渡。

## 9. 第四轮：立绘改成抽象层，默认什么都不画（用户验收后，2026-09-23）

用户看真机后提了四条，全部成立，其中前两条是同一个根因：

1. **「控制台里已经把模块关掉了，立绘还在」**——真 bug，且不是「关漏了一处」而是**结构上关不掉**：
   `IconBackdrop.Current` 是个静态全局量，初值 `Default { On = true }`；那张独立设置卡只在
   `OnActivate`/`OnUpdate` 里同步它，而 `OnUpdate` 只对**已激活**的模块跑。卡从没激活过时没人写过这个值，
   静态默认值就是「开」；此时再去关它，`SetEnabled` 见 `entry.Enabled == false` 直接 return，
   `OnDeactivate` 根本不触发——面板上关不动，屏上照旧铺。
2. **「不该是新增一张卡，该是一层抽象」**——立绘参数属于「这个 IDE 的消息长什么样」，
   所以它是 IDE 消息模块的**基类**，不是一张不认识任何 IDE 的通用设置卡。
3. **「没有指定 icon 就不要显示**（屏幕上那个居中的圆角矩形）——把「默认画一点什么」这个念头整个删掉。
4. **「别让面板管理抽象类」**——`WatchModuleRegistry.Start` 的反射扫描本来就跳过 `IsAbstract` 与
   没有公共无参构造的类型，这条已在；本轮把它**测出来**（见下）。

做法：

- `Services/Modules/IconBackdropModule.cs` 从 `sealed` 卡改成 **`abstract` 基类**：
  在子类的行之后固定追加七行（`bd-on` / `bd-icon` / `bd-size` / `bd-x` / `bd-y` / `bd-opacity` / `bd-preview`），
  `Fields`/`Metas`/四个生命周期入口全由基类占住，子类实现 `OwnFields()` 与 `OnIdeActivate/Update/Deactivate/ValuesPushed`——
  **没有「子类忘了接」这条路**。`QoderWatchModule` 与 `IdeStatusModule`（Trae/ZCode/Codex/VS Code/DSH 五张卡的基类）都改继承它。
- 子类新增一个必须实现的 `IdeSource`：这张卡认领哪个 `-from` 来源。它同时用于 `IdeProbe.LastRealEvent`
  的日志过滤（原来五处硬编码的平台词改为读它），一处声明，立绘与徽章两边都对上。
- 发布面从「一个全局开关」改成 **来源 → 参数**的表（`IconBackdrop.Publish/Retract/TuningFor/Resolve`）：
  只有「模块激活」且「勾了 bd-on」才发布，任一条件不满足就撤回；表里没有 = `Resolve` 返回 null = 那一层不画。
  于是**没有静态默认值可漏**，也就没有「关不掉」。
- 摆放参数只在有人认领时来自那张卡；命令自带 `-icon` 时按中性摆放画那一条（指定了就照指定的看，
  那张图当剪影不合格就是不画，不悄悄退回来源同名图）。
- 面板噪声：`bd-on` 没勾时把几何与试弹五行 `Visible=false` 收起来，只留开关与图标两行。

验证（判定器本身先自证）：

- `module-protocol-check` 53 → **71 项**：两层基类都不在面板上、面板上每个模块都可实例化、
  反射扫描没把抽象类送到 `Activator` 跟前（靠日志里的「构造失败」痕迹盯，见下）、每张 IDE 卡都挂着那七行、
  **一张卡都没激活时发布表必须是空的**；再用假 IDE 卡走真宿主验运行时行为：
  未激活不发布 → 勾了才按默认发布 → 越界钳回 200 / 字母退回 50 → 试弹带派生 tag 且不带 `-replay` 并按完复位
  → 取消勾选与关掉整张卡都立刻撤回并收掉自己那条试弹。
- `effect-schedule-check` 88 → **95 项**：`Resolve` 的六条判据（没人认领不画、裸消息不画、显式 `-icon` 画、
  指定的图不合格就不画、认领后按卡的摆放画、撤回后立刻不画），图用临时目录里现写的 png 夹具。
- 两条对照都做过（否则等于没测）：把 `bd-on` 的默认值改回 `true` → 2 项红；把反射扫描的两道判据
  （`!t.IsAbstract` 与公共无参构造）**一起**摘掉 → 「构造失败痕迹」那条红（只摘一道不行：抽象类的构造函数是
  protected，另一道还会挡住，那就不在测这条性质了）。
- `e2e-backdrop.ps1` 2 → **3 项**：正向腿从 `-from qoder` 换成显式 `-icon <真图>`，并新增用户报的那条
  「`-from qoder` 但没有卡认领 → 那块区域必须还是空的」。
- `selftest.ps1` 58 项不回归（本轮没碰 hook 脚本）。

## 10. 第五轮：擦出住进预算里，边框等消息彻底走完再收（2026-09-23）

用户验收后提的第一条：「消息结束太快了，动画没有播放完毕 —— 应该是消息完全收起之后全屏 border 才淡出，
而不是消息还没播完就直接关闭 border 效果。」

根因是**两个时钟对不上**：一行的预算 `ScreenSeconds = 淡入 + 持续 + 淡出`，可效果窗把擦出**接在预算之后**
又另花一个淡出。于是 `Until` 那一刻调度器以为屏幕空了（`Tick` 摘行 → `Pump` 上下一条），
而窗上那一行其实才刚开始往外擦：换组走 `Banner(fresh)` 的 `StopGroup + ClearRows`，正在擦的上一行被当场抹掉；
`off` / 紧急抢屏同理。全屏边框的淡出也挂在同一套判点上，看着就是「border 抢在正文走完前先关」。

- 新增 `Services/EffectTiming.cs`（纯函数）：`ExitStart(entryDone, until, exitSeconds) = max(entryDone, until − 淡出)`，
  擦出从那一刻开始、到 `Until` 恰好擦完 —— 于是「屏幕让位时刻 == 最后一条真的消失时刻」这条等式成立，
  窗口与调度器对同一个时刻说话（调度器 200 ms 心跳只会晚摘不会早放，是安全方向）。
  唯一例外：入场被同行错峰挤后而预算又短，宁可比预算多留一会儿也不腰斩入场。
- 边框定级改看**还在占位的行**（`Until > now`，擦到一半的也算），所以最后一行彻底消失后 `RefreshBorder`
  才花 0.5 s 淡掉边框与立绘；四行上限与 twin 归并仍按 `!Exiting`（那是动画状态，不是占位状态）。
- 副作用（是对的）：一条消息占屏总长回到文档一直写的「三段之和」，比原来少一个淡出。

## 11. 第六轮：消息上屏甩一颗粒子（IDE 图标 + 类型角标）（2026-09-23）

用户提的下一条：粒子此前只在彩蛋关键词上出现（`KeywordWatcher` → `Emit`），对话消息上屏时没有。

  没有领词的手写命令才退回 `-s` 档位（紧急/error → ❌，warn → ❓，其余 → ✔）。

## 12. 第七轮：流光溢彩模式（边缘彩色球 + 中心淡出遮罩）（2026-09-23）

用户要的效果：屏幕四周一些彩色渐变圆，**相邻两球必须色相靠近**，中间靠一层淡出遮罩保持透明穿透，
只有边缘变彩色。他同时问了另一条路："web 上是不是有更快的做法，比如直接把颜色设成一个颜色序列？"
—— 两条都渲染出来量过，结论在 `shots/aurora-*.png`（离屏 `RenderTargetBitmap`，不开窗、不占屏）。

**判据本身要能算**：`Services/AuroraField.cs` 是纯函数（球位/色相/遮罩色标/HSL→RGB），
离屏工程 `release/typing-games/aurora-proto` 渲染后直接量像素，15 项：
环上采样 alpha 的第 10 百分位（"一整圈都在发光"，探四个点会被"球心刚好不在那"骗过去）、
四角同一指标（允许暗一档）、中心 50%×30% 区域最大 alpha ≤ 26（正文不能有颜色）、
相邻球色相差 ≤ 34°、环接头不跳色、8 秒后同一取色点色相真的转了。

**离屏量出来的四个真问题**（每个都是先红后修）：
1. 每颗球各自 ±9° 的色相抖动直接叠到相邻差上：设计的 30° 变 35.8°，越线 → 抖动改成**全圈共用**，
   要活起来交给位置与亮度。
2. 球按**角度**均分在内切椭圆上 → 四角一点球都没有（角上 alpha 19，等于四角是黑的）→ 换超椭圆（方度 3.2）。
3. 超椭圆上按**分数空间**弧长均分 → 分数 0.17 的横向步长是 330 px、纵向只有 183 px，球全挤到上下边
   → 弧长必须按像素算（带屏幕比例）。
4. 11 颗球（半径 280-390 px）在 6000 px 周长上间隔 545 px → 球之间漏缝（环 p10 只有 37）→ 默认 16 颗。
另外量法本身错过一次：用"椭圆半径 0.95-1.05"划采样带，而矩形的角在半径 1.41 处，
那条带子根本框不到角（角上恒 0，看着像产品坏了其实是判据坏了）→ 改成"到最近那条边的距离 ≤ 6%"。

**两条路的结论**：`aurora-band-sequence.png`（直接给四条边铺色序）中心也能保住全透，但它是**硬边直条** ——
每条边各自跑一遍色序，角上能看到两条渐变各自收尾的接缝，也不会向内晕开（向内 8% 处 alpha 已经归零，
球那版还有 70 左右）。要"五彩斑斓但不廉价"就得要 bloom，所以接的是 A 那条：
XAML 加 `Aurora` 层（一个 Canvas + 一层径向遮罩），每帧按 `AuroraField` 改色改位（画刷刻意不 Freeze），
换组才重铺球；收的时候跟边框同一时刻淡掉（边缘色不能留在桌面上）。命令行 `-aurora on|off [球数]`，默认关。

验证：`effect-schedule-check` 104 → 128 项（含 `-aurora` 段的九条解析：只写段名也算开、
球数夹 6-24、写文字整条不认、**"写了段名没带参数"与"根本没写"必须分得开** —— 这条用空表判过，
结果所有命令都被点亮）、`aurora-proto` 15 项、`module-protocol-check` 74 项不回归，build 0 警告。
真机上还要看的：16 颗球在 5120×1440 双屏上的帧开销、光晕厚度（遮罩内缘 0.62）合不合口味。

## 13. 第八轮：测试流程重排（用户点名的一条"串行"其实来自测试自己，2026-09-23）
